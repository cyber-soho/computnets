Module 11 · Computer Networks · Weeks 12–13

Final Project Integration & Optimization

Project Phase 11 — the closing piece of the continuous semester project.

From the Industry to the Classroom — Building the IT's Future, Today and Together!

For the past eleven weeks you have been quietly assembling a real-looking enterprise network. Each week added one floor to the building. This week you become the building inspector, the cleaner, and the architect who hands the keys to the new owner — all at once.

The official name of this work is Project Phase 11 — Final Integration & Optimization, and it spans two class weeks (Week 12 and Week 13). Everything you submit at the end of Week 13 must read as a single, coherent system — not a stack of weekly homework.

A small reminder before we start: do not panic. You have already built almost everything. Phase 11 is the moment you connect the dots, not the moment you invent new dots.

By the end of these two weeks you will have:

  1. Re-read every device's running-config and applied an optimisation pass across the whole topology.
  2. Updated the IP plan and both topology maps to match the network that actually exists right now.
  3. Designed and run at least six end-to-end test scenarios covering same-VLAN, inter-VLAN, DHCP, WAN, traceroute, and a deliberate failure.
  4. Captured at least one Wireshark snapshot of ICMP or ARP traffic from your topology.
  5. Written a strict four-page A4 report with five well-defined sections.
  6. Produced an honest Limitations & next steps paragraph, including whether Phase 10 was performed or skipped.
  7. Bundled the whole deliverable into a single ZIP archive.
Part 1

The 1-2-1 Ponderation

Theory · Implementation · Documentation — and why implementation is weighted twice.

In one sentence

The rest of the course used a 1-2-2 weekly rhythm (one hour of lecture, two hours of lab, two hours of independent work). The final deliverable of Phase 11, however, is graded with the 1-2-1 ponderation — a different beast entirely.

The 1-2-1 ponderation distributes your final mark across three components: theory, implementation, and documentation, with implementation weighted twice as heavily as either of the other two.

1-2-1 — your final mark, broken down

Theory · Implementation · Documentation

25%
Theory & understanding
Short oral check or quick-fire questions during the review session — why you typed each command, not just that you typed it.
50%
Lab implementation
Does the network actually run? Does an HQ host ping a Branch host? Are VLANs (Virtual Local Area Networks) isolated as designed? Real life rewards what runs, twice as much.
25%
Documentation
The four-page report you will hand in. The grade reflects how readable, accurate and useful the document is for the next engineer who inherits the network.

Implementation carries double the weight of either of the other two. That is on purpose.

Read this twice

Honesty in operations is part of the grade. A working network with an honest report beats a half-broken network with a polished one. Pretending always loses points.

Part 2

Newbie Glossary

The vocabulary of network operations, in plain words. Read this before you start.

The bullet-points of Phase 11 sound short, but every single phrase hides a small mountain of network-operations vocabulary. Here is a quick rope to hold while you climb. If you already know a term, skip it; if you half-know it, read it again.

Final Integration
Taking the parts you built in isolation (one VLAN here, one router there) and proving they work together, the way a finished car proves the engine works with the brakes and the steering. Until you integrate, you have parts. After integration, you have a system.
Optimization
Making something already-working work better: faster, cleaner, easier to read, less wasteful. In networking it usually means tidying up CLI configurations, removing useless lines, and fixing default values you left at “factory” because you were busy six weeks ago.
End-to-end testing (E2E)
Sending real-looking traffic from one corner of the network all the way to the opposite corner and verifying every hop along the way. If the user in Branch HR can reach the file share at HQ, the test passes. If she cannot, you have not finished.
Topology map
A drawing of the network. Boxes for devices, lines for cables, labels for interfaces (the physical or logical port on a device — Fa0/1, Gi0/0/0, etc.) and IP (Internet Protocol) addresses where they matter. Two flavours exist:
  • Logical topology — shows VLANs, subnets, routing — the idea of the network.
  • Physical topology — shows the actual cables, racks, ports — the reality of the network.
  • You will produce both.
IP table (IP plan / IP allocation table)
A spreadsheet-like list that says, for every subnet: the network address, the mask, the gateway, the DHCP (Dynamic Host Configuration Protocol) range, the static reservations, and a short comment (“HR users”, “Engineering printers”, “WAN link to Branch”). Future-you will worship past-you for keeping this current.
Configs
Short for device configurations. The text output of show running-config on a Cisco device. One file per device. The export of every brain in your network.
Hardening
The polite word for making the network harder to attack. Disabling unused ports, replacing Telnet (insecure remote login over TCP/23) with SSH (Secure Shell — encrypted remote login over TCP/22), configuring port-security, and so on. This was Phase 10. Phase 10 is optional in this course, so we presume you have not done it. That is fine. Your final report will simply be honest about it.
Backup
A saved copy of a configuration outside the device itself. Phase 10 introduced TFTP (Trivial File Transfer Protocol) for backups. If you skipped Phase 10, substitute any method that produces a text file you can re-paste later: copy-paste into a .txt file, push to a personal Git repository, e-mail it to yourself — anything that survives a device reload.
Convergence
The moment after a change (a link goes down, a route is added) when every router has finished updating its tables and the network is “calm” again. End-to-end tests right after a change can fail simply because convergence has not finished. Wait a few seconds, then test.
NOC (Network Operations Center)
The room (or shared screen) where engineers watch the network all day. Documentation lives here in real life. Pretend yours is a NOC — the report is what you would hand the NOC team on day one.

If a term in the rest of this assignment is not in this glossary and is not obvious, look it up before continuing. Looking things up is half of network operations.

Part 4

Phase 11 — what you actually do

End-to-end testing, configuration optimisation, and the documentation deliverable.

The official syllabus describes Phase 11 in three short bullets. We unpack each in turn.

1. Full end-to-end testing

The goal is to prove that the network behaves as designed, from one user-facing endpoint to another. You will design at least six test cases and run them all. Six is the minimum; more is better.

How to design a test case

Each test case has six parts: a clear name, a source, a destination, the path you expect the packet to take (which devices, which interfaces), the expected result (success, partial success, deliberate failure), and the observation — what really happened. Format is up to you (table, list, one paragraph each). Pick what reads cleanly.

The six minimum scenarios

Same-VLAN reachability inside HQ

A host in HR pings another host in HR. Validates Phase 4

Inter-VLAN reachability inside HQ

A host in HR pings a host in Engineering. Validates Phase 5

DHCP working across a relay

A new host in a remote VLAN gets an IP from the central DHCP server. Validates Phase 7

HQ-to-Branch reachability

A host in HQ pings a host in the Branch over the WAN link. Validates Phase 9

Trace the path

Run traceroute (tracert on Windows clients) from #4 and confirm every hop matches your topology drawing. Validates Phase 1 against reality

Negative test — break it on purpose

Shut down one link, repeat scenario 4, observe what happens. Then bring the link back up and watch convergence. Validates Phase 6 thinking

For each scenario, keep a short screenshot or copy-paste of the CLI output. The report will reference these directly. If your simulator lets you export a packet capture, do it for at least one scenario — a Wireshark snapshot of an ICMP (Internet Control Message Protocol) echo-request / echo-reply pair is a small piece of evidence with a lot of pedagogical weight.

Tip from the field

Real outages rarely look like “nothing works.” They look like “it works for some users and not others, and only on Tuesdays.” Cultivate the habit of writing down what you tested and what you did not. The list of not-tested items is part of the deliverable; honesty in operations is non-negotiable.

2. Optimizing configurations

Optimization is not a refactor. You are not throwing your work away. You are walking through every device's running-config, line by line, and asking three questions:

  1. Is this line still needed? If you typed it in Week 3 because the textbook said so, and you have not used the feature since, comment on it in your report. Don't necessarily delete it — but acknowledge it.
  2. Is this line consistent with the others? Naming conventions, MTU (Maximum Transmission Unit) values, password algorithms, banner texts. Inconsistency is the seed of every future midnight call.
  3. Is the description meaningful? Cisco interfaces accept a description command. Use it. “Uplink to MAD-HQ-SW1 Gi0/1 — VLAN 10/20/30 trunk” is documentation that travels with the device. “To switch” is not.
Concrete optimisation checklist (apply to every device)
  • Hostname matches the device's role and site (e.g., MAD-HQ-R1, BCN-BR1-SW1).
  • Console and VTY (Virtual Teletype — the remote-management lines) have an idle exec-timeout (5 minutes is sensible).
  • Every active interface has a description.
  • Every unused interface is shutdown (yes, even without Phase 10 hardening — closing unused doors is plain hygiene).
  • The default route, if you use one, points to the right next-hop.
  • The DHCP pool excludes the gateway and the static reservations.
  • ACLs are read top-to-bottom: more specific rules above more general ones.
  • A banner motd (Message Of The Day) exists on every device with a clear “lab equipment, do not abuse” notice.

Click each item to mark it done as you go through your devices. The state is local to your browser — do not rely on it surviving a reload.

No two networks are optimised the same way

Use the list above as a starting point, not a holy scripture. If you find something else to clean up, write it down in the report and explain why you cleaned it.

3. Finalising the Network Documentation deliverable

This is the artefact your future-self, your grading panel, and any imaginary engineer who inherits your work will actually open. Treat it as a product, not as homework.

The Network Documentation deliverable contains four parts, all submitted as a single ZIP archive:

  1. The four-page A4 report (PDF or DOCX) — the centrepiece, described in the next section.
  2. Topology maps — at least two diagrams (logical and physical). Acceptable formats include PNG, SVG, or PDF exports from your drawing tool. Each diagram includes a title, a date, and a small legend.
  3. The IP plan table — a spreadsheet (XLSX, ODS, CSV) or a clean Markdown table. Columns at minimum: VLAN ID, name, network/mask, gateway, DHCP range, static reservations, comments.
  4. Device configurations — one text file per device, named after the hostname (MAD-HQ-R1.txt, BCN-BR1-SW1.txt, …). Pure running-config exports, nothing else.

If your project uses fancier tooling — a Git repository, a wiki, a NetBox instance — feel free to mention it in the report and include the link or the export. The substance is what counts; the container is yours to choose.

Part 5

The four-page A4 report — strict spec

Five sections, four pages, one PDF. Cut don't pad.

Read this carefully. Going over four pages does not earn extra points; it loses them. We are training the discipline of saying things in fewer words. Brevity is a senior engineer's super-power.

Format

  • A4, portrait, margins of about 2 cm on all sides.
  • Body font 10–11 pt, headings up to 14 pt. Plain, readable, no decorative fonts.
  • Single column. Page numbers in the footer.
  • Tables and small inline diagrams are welcome. Do not paste full CLI dumps — those go into the configurations folder.
  • Submit as PDF. If you write in Word, LibreOffice or Markdown and export, that is fine; just send the PDF.

Structure — five sections, in this order

1. Cover block (top of page 1, ~¼ page)

Student name, group, date, project title (Multi-Branch Campus Network), one-sentence executive summary (“This network connects HQ in Madrid with a Branch in X, supports Y users across Z VLANs, and …”).

2. Topology overview (rest of page 1 to top of page 2)

Small inline logical-topology diagram (it can be a thumbnail of the larger PNG you submit separately), plus a short paragraph that explains the design choice in plain words. Reference the larger diagram by filename.

3. End-to-end test results (page 2 to mid page 3)

A single, well-formatted table with the six (or more) scenarios, source, destination, expected result, observed result, status (Pass / Fail / Partial). One or two sentences of commentary at the end.

4. Optimisations applied (mid page 3)

A short bulleted list of the cleanups you actually performed during Phase 11, with a one-line why next to each. If you applied something from the Phase 10 (Hardening) topics on your own initiative — for example, you decided to enable SSH because it was easier than expected — say so here. Honesty is graded.

5. Limitations & next steps (page 4)

What you did not test, what you would do differently if you had another week, what the next engineer should know. A brief note here explicitly stating whether Phase 10 (Hardening) was performed or skipped is required. This is where future-you (or a real-life colleague) thanks present-you.

Voice and tone

Write as if you were explaining the network to a senior engineer who joins the team next Monday and has one coffee to read your report. Direct, unshowy, technically honest. No marketing prose, no “we successfully implemented”, no padding. If a section is shorter than expected because the work was simple, leave it short.

Part 6

About the (skipped) Phase 10

Hardening was optional. We presume you skipped it. Here's how to handle that honestly.

Phase 10 — Hardening the Infrastructure — was the optional security-focused phase that included SSH instead of Telnet, port-security on access ports, and TFTP backups. The course explicitly accepts that students may not have implemented it.

This means…

  • You must not pretend you did Phase 10. The grade is unaffected by the absence; it is harshly affected by an inaccurate report.
  • Your end-to-end tests should focus on functional behaviour (does it work?), not on security behaviour (is it safe from attackers?).
  • In the Limitations & next steps section of your report, write a small honest paragraph along these lines:
    “Phase 10 hardening was not performed. As a consequence, remote management uses Telnet, no port-security is configured, and there is no automated configuration backup. The recommended next step is …”
    — and recommend something concrete.
Voluntary partial hardening

If you want to do some of Phase 10 voluntarily — for example, just enabling SSH on one device — please do, and report it in the Optimisations applied section. Voluntary security improvements are always welcome, never punished.

Part 7

Two-week timeline — at least 3 h per week

A rhythm that works in practice. Use it as a starting point.

You have at least six hours total to dedicate to Phase 11 across the two weeks (3 h × 2). Most students need a little more, especially for the report. Below is a rhythm that has worked well in practice.

12
Week · discover & clean

Read what past-you wrote, then tidy.

  1. Re-open every device's running-config. Take notes. Do not change anything yet. You are reading what you wrote weeks ago. You will be surprised.
  2. Apply the optimisation checklist. Hostnames, descriptions, idle timeouts, banners. Save and reload to make sure your changes survived.
  3. Update the IP plan table and the topology maps to match the current state of the network. If a VLAN was added in Phase 9 and never made it into the IP plan — fix that now.
13
Week · test & write

Prove it works, then describe it.

  1. Run the six end-to-end test scenarios. Capture screenshots. If a test fails, decide whether to fix it or document it as a known gap. Both choices are valid.
  2. Draft the report — get all five sections on paper, even badly. The first draft is meant to be ugly.
  3. Tighten the report to four pages. Cut, do not pad. Export to PDF. Build the ZIP archive with all four parts of the deliverable. Submit.

If you have time on top of that, consider implementing one item from Phase 10 voluntarily and adding it to the report. Habits formed in a learning environment travel with you for years.

Part 8

Tools — pick yours, justify your choice

Open-source, replaceable, and yours to substitute or to invent.

Read this before you pick anything

Every tool listed below is “open” in the sense that matters here: open-source, free for educational use, or available as an industry-standard free download. They are listed as a starting point, not as a closed set.

You are free, and frankly encouraged, to substitute any of them with a different tool you find more powerful or more comfortable. You are also encouraged to create your own small tools (a Python script, a Bash one-liner, a tiny web page) when none of the existing ones fit your need.

The grading does not care whether you used Tool A or Tool B. The grading cares that the deliverable is correct, that you understand why the tool was the right choice, and that you can defend that choice in the review.

Network simulators

Cisco Packet Tracer (the one we use in class), GNS3, EVE-NG. Any of them will run the topology.

Diagram drawing

diagrams.net (formerly draw.io), Inkscape, or even hand-drawn diagrams scanned to PDF. Cisco's icon set lives at Cisco's brand assets page.

Packet capture

Wireshark is the de-facto standard. Most simulators export .pcap files Wireshark can open.

IP plan / spreadsheets

LibreOffice Calc, Google Sheets, or any plain Markdown table. Industry-grade alternative: NetBox.

Document writing

LibreOffice Writer, Microsoft Word, Pandoc, Typst, LaTeX. Whatever you write in, hand in PDF.

Backups (voluntary Phase 10)

tftpd-hpa for Linux, Tftpd64 for Windows, or simply git. Pick one.

Reference standards

When in doubt, consult the source: IETF (Internet Engineering Task Force), IEEE (Institute of Electrical and Electronics Engineers), Cisco's networking documentation, and the Cisco Networking Academy.

URL safety

Always check unfamiliar URLs through VirusTotal before opening on a managed laptop.

If you research a niche tool that turns out to be brilliant, mention it in the report's Limitations & next steps section. That kind of curiosity is exactly what the industry rewards.

Submission checklist

When you submit, the ZIP archive (named MOD11-Phase11-Surname-FirstName.zip) must contain at minimum:

  • report.pdf — the four-page A4 report.
  • topology-logical.png (or .svg / .pdf).
  • topology-physical.png (or .svg / .pdf).
  • ip-plan.xlsx (or .ods / .csv / .md).
  • configs/ — folder with one text file per device.
  • tests/ — folder with the screenshots / packet captures referenced in the report.
  • (optional but recommended) README.md — one-page index of what is in each file.

Click each line to tick it off as you build the archive. Late submissions are accepted but reduced by 10 % per working day.
